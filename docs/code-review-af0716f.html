1. 알 수 없는 1xx 코드에 근거 없는 "악용된 정상 도메인" 안내

checker-core/…/check/rbl/SpamhausDblProvider.java:79

isAbusedLegit()이 meaning != null 확인 없이 last octet 100~199 범위만 검사한다. Spamhaus가 새 코드(예: 127.0.1.110)를 추가하면 evidence에는 "알 수 없는 리턴 코드"라고 표시하면서 guidance는 "사이트 해킹·오픈 리다이렉터 악용이 원인"이라고 단정 — 증거와 안내가 서로 모순된다.

직접 등재 분기는 else if (meaning != null)로 가드되어 있는데, 악용된 정상 도메인 분기에만 가드가 없다.

분류를 숫자 범위가 아닌 LISTINGS 맵 멤버십(102~106)에서 도출. 미지 코드는 특정 guidance 없이 일반 안내로 폴백.
CONFIRMED

2. 미지 코드에서 check.spamhaus.org URL 소실 (회귀)

checker-core/…/check/rbl/SpamhausDblProvider.java · DomainRblCheck.java:72

이전 커밋까지는 어떤 도메인 등재든 무조건 https://check.spamhaus.org … 안내가 나왔다. 이제 LISTINGS에 없고 100~199 범위 밖인 코드(예: 127.0.1.7, 127.0.1.50)는 guidance가 빈 리스트로 반환되고, DomainRblCheck의 폴백 문구("도메인 등재 사유를 확인하고 각 RBL의 해제 절차를 진행하세요")에는 URL이 없다.

사용자가 조회 링크를 가장 필요로 하는 미지 코드 상황에서만 링크가 사라지는 정보 회귀.

폴백 문구에 check.spamhaus.org URL 복원, 또는 미지 코드에도 조회 URL을 담은 기본 guidance 부여.
CONFIRMED

3. 두 집계기의 폴백 정책 비대칭 (복붙 분기)

checker-core/…/check/rbl/RblCheck.java:114 vs DomainRblCheck.java:69

guidance 수집 루프(LinkedHashSet → addAll → forEach)가 두 파일에 거의 그대로 복사됐는데, RblCheck는 일반 안내를 항상 내보내고 DomainRblCheck는 비었을 때만 내보낸다.

지금 당장 재현 가능: DBL 응답에 알려진 코드 + 미지 코드가 함께 오면 미지 등재에는 안내 줄이 하나도 없다 — 폴백은 set이 비어있지 않아 스킵되기 때문. 향후 두 번째 DomainRblProvider(예: SURBL) 추가 시에도 동일한 구멍이 생긴다.

폴백 정책을 한쪽으로 통일(권장: RblCheck처럼 일반 안내 상시 방출)하거나, 수집·방출 로직을 공용 헬퍼로 추출.
CONFIRMED

4. DQS 키 없는 배포에서 "고정 IP" 근본 해결 안내 소실

checker-core/…/check/rbl/RblCheck.java:116 · SpamhausZenDqsProvider.java (DELISTING)

동적 대역 관련 조언("고정 IP/정식 발신 경로 사용이 근본 해결책")이 ZEN의 DELISTING 맵(127.0.0.10/11)으로만 이동했다. ZEN은 DQS 키가 없으면 enabled()=false로 스킵되므로, 키 없는 배포에서 동적 IP가 PSBL/Barracuda에 등재되면 근본 원인 힌트를 못 본다.

단, 기존 문구도 PBL 미등재 상황에서 오해 소지가 있었으므로 단순 복원보다는 개선이 적절하다.

일반 안내에 중립 문구 추가: "동적/가정용 대역이라면 고정 IP 사용이 근본 해결책" (PBL 단정 없이).
CONFIRMED

6. isAbusedLegit의 무방비 Integer.parseInt

checker-core/…/check/rbl/SpamhausDblProvider.java:91

실제 dnsjava 경로에서는 A 레코드가 항상 dotted-quad라 사실상 안전하지만, DnsQueryService는 교체를 전제로 한 인터페이스다. 비숫자 값이 오면 NumberFormatException이 DomainRblCheck.run() 밖으로 전파되어 카드 전체가 ERROR — 실제 LISTED 결과를 가린다.

7. 에러 코드가 루프 중간에 등재 결과를 버림

checker-core/…/check/rbl/SpamhausZenDqsProvider.java:88 (SpamhausDblProvider 동일 패턴)

[127.0.0.2, 127.255.255.254] 같은 혼합 응답이면 이미 수집한 확정 등재(SBL)를 버리고 RblVerdict.error()를 반환 — 카드가 FAIL 대신 WARN "확인 불가"가 되고, DNS 레코드 순서에 따라 결과가 갈린다. Spamhaus가 실제로 혼합 응답을 주는지는 미확인(쿼리 거부는 보통 전체 응답 조건)이라 PLAUSIBLE.

루프를 끝까지 돌고 등재가 하나라도 있으면 LISTED 우선, 등재 없이 에러 코드만 있을 때 ERROR 반환.
PLAUSIBLE

8. RblVerdict에 null 방어 없음 + 사장된 1-arg 팩토리

checker-core/…/check/rbl/RblVerdict.java:13, 22

compact constructor가 없어 미래 provider가 null guidance를 넘기면 집계 시점(delistingGuidance.addAll)에 NPE로 카드가 ERROR가 된다 — 등재되어 FAIL이어야 할 바로 그 순간에. 현재 호출처는 모두 안전하지만 "provider 추가"가 이 저장소의 공식 확장 지점이다.

또한 1-arg listed(listings) 팩토리는 이 커밋으로 호출처가 0곳이 됐다 — 남겨두면 미래 provider가 guidance 없는 LISTED를 조용히 만들 수 있다.

compact constructor에서 Objects.requireNonNull + List.copyOf, 1-arg listed() 삭제로 guidance 명시를 컴파일러가 강제.
