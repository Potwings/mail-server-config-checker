3분 배경지식 — 메일 인증은 왜 이렇게 복잡한가

이미 SPF/DKIM/DMARC를 아신다면 전체 지도로 건너뛰세요.

문제: SMTP는 발신자를 확인하지 않는다

1982년에 설계된 SMTP에는 인증이 없습니다. 누구나 아무 주소로나 메일을 보낼 수 있죠. 그래서 누가 이 도메인을 대신해 메일을 보낼 수 있는가를 나중에 덧붙인 것이 SPF·DKIM·DMARC 3종 세트입니다.

여기서 반드시 구분해야 하는 것이 주소가 두 개라는 사실입니다.

S: MAIL FROM:<bounce@mail.shop.co.kr>     ← ① 봉투 발신자 (envelope from)
S: RCPT TO:<user@example.com>
S: DATA
S: From: 고객센터 <help@shop.co.kr>        ← ② 헤더 발신자 (From:)
S: Subject: 주문 확인
S: ...
  • ① 봉투 발신자 — SMTP 대화에서 오가는 값. 반송 메일이 돌아갈 주소이고 사용자에게는 안 보입니다.
  • ② 헤더 발신자 — 메일 프로그램에 표시되는 주소. 사용자가 보는 값입니다.

이 둘은 서로 달라도 됩니다. 그리고 이 “달라도 된다”는 점이 DMARC alignment가 필요해지는 이유이자, 이 프로젝트에서 가장 헷갈리는 부분입니다.

세 가지 인증 기술

기술무엇을 검증하나사용하는 주소근거 자료
SPF이 IP가 이 도메인을 대신해 보낼 자격이 있나① 봉투 발신자 도메인DNS TXT
DKIM이 메일 내용이 서명 이후 변조되지 않았나서명의 d= 도메인헤더의 전자서명 + DNS 공개키
DMARC위 둘 중 하나라도 사용자가 보는 From:과 같은 도메인으로 통과했나② 헤더 발신자DNS TXT

DMARC의 존재 이유가 여기 있습니다. SPF와 DKIM은 각자 자기가 아는 도메인만 검증하므로, 공격자가 자기 도메인(evil.com)으로 SPF를 완벽히 통과시키면서 From: ceo@bank.com을 쓰는 것을 막지 못합니다. DMARC는 “인증에 성공한 도메인이 화면에 보이는 From:과 같은 조직이어야 한다”는 조건(alignment)을 추가해 이 구멍을 막습니다.

그 외 이 도구가 보는 것들

  • PTR / FCrDNS — IP를 역방향 조회하면 호스트명이 나오고, 그 호스트명을 다시 정방향 조회하면 원래 IP로 돌아와야 합니다. 안 되면 다수 수신 서버가 스팸 신호로 봅니다.
  • RBL — 스팸 발신 IP 블랙리스트. 203.0.113.5는 옥텟을 뒤집어 5.113.0.203.zen.spamhaus.org를 A 레코드로 조회합니다. 응답이 오면 “등재됨”.
  • MX — 이 도메인의 메일을 받아줄 서버 목록.
  • MTA-STS / TLS-RPT — 서버 간 구간의 TLS를 강제하고 실패를 리포트받는 표준.

CHAPTER 1뼈대 만들기 — Check 인터페이스와 병렬 엔진

다루는 커밋: 91475b4 · d3ff40b (M1) · fe654e6

배경 — 진단 도구가 풀어야 하는 구조적 문제

메일 서버 진단 도구는 겉보기엔 단순합니다. DNS를 몇 번 조회하고 결과를 보여주면 되니까요. 하지만 실제로 만들어보면 세 가지 성가신 성질이 드러납니다.

  1. 검사 항목이 계속 늘어난다. 이 프로젝트만 해도 SPF에서 시작해 최종 12개가 됐습니다. 검사를 추가할 때마다 엔진·API·UI를 고쳐야 한다면 금방 무너집니다.
  2. 어떤 검사는 반드시 느리다. RBL은 6개 존에, 전파 검사는 리졸버 6곳에 조회를 던집니다. 하나가 타임아웃되면 나머지가 다 끝나도 사용자는 계속 기다립니다.
  3. 결과가 통과/실패로 표현되지 않는다. Spamhaus 키가 없어 조회를 못 한 것은 통과도 실패도 아닙니다. “확인 불가”와 “문제 없음”을 절대 섞으면 안 됩니다.

M1 커밋은 코드를 거의 쓰지 않고 이 세 문제에 대한 답만 정해놓은 커밋입니다.

직관

검사 하나를 “함수”로 못 박기

public interface Check {
    String id();       // "spf", "dmarc" — API 응답에 쓰이는 안정적 식별자
    String title();    // UI에 보이는 이름
    CheckResult run(CheckContext context);
}

주석에 못 박힌 조건이 하나 있습니다.

Implementations must be stateless and thread-safe: the engine runs all checks concurrently against the same context.

검사 구현체는 상태를 갖지 않습니다. 그래서 엔진이 마음대로 병렬 실행할 수 있고, 스프링 빈으로 싱글턴 하나만 두면 됩니다.

결과를 5단계로 나눈 이유

public enum CheckStatus {
    PASS(0), SKIP(1), WARN(2), ERROR(3), FAIL(4);
}

괄호 안 숫자가 심각도입니다. 이 숫자 하나가 뒤에서 아주 유용해집니다.

상태의미실제 사례
PASS문제 없음SPF 레코드가 정상이고 -all로 끝남
SKIP검사 자체를 못 함Spamhaus DQS 키 미설정 / 메일 원문 없음
WARN동작하지만 권장에 못 미침p=none DMARC, RSA 1024비트 DKIM 키
ERROR조회 실패로 판정 불가DNS 타임아웃, 검사 예외
FAIL명확한 설정 오류SPF 레코드 2개(RFC 위반), RBL 등재

핵심은 SKIP과 PASS를 갈라놓은 것입니다. “확인 못 했음”을 “괜찮음”으로 보고하면 사용자를 속이는 도구가 됩니다. 이 원칙은 PRD 핵심 제약에도 명시돼 있고, 뒤에서 RBL 오류 코드 처리에서 다시 등장합니다.

근거와 가이드를 분리한 결과 객체

public record CheckResult(String checkId, String title, CheckStatus status,
                          List<String> evidence, List<String> guidance, long elapsedMs)
  • evidence — 왜 이 판정이 나왔는지. "레코드: v=spf1 include:_spf.google.com ~all"
  • guidance — 어떻게 고치는지. "레코드 끝에 ~all 또는 -all을 추가하세요"

진단 도구가 “SPF 설정에 문제가 있습니다”만 말하면 쓸모가 없습니다. 근거와 처방을 구조적으로 분리해 두면 UI는 두 목록을 다르게 그리기만 하면 됩니다.

빌더에 재미있는 메서드가 하나 있습니다.

/** Raises the status only if the new one is more severe. */
public Builder atLeast(CheckStatus s) {
    if (s.isWorseThan(this.status)) { this.status = s; }
    return this;
}

검사 하나가 여러 문제를 발견할 수 있습니다. 구문 경고(WARN)가 있으면서 lookup 한도도 넘었다면(FAIL) 최종 상태는 FAIL이어야 합니다. atLeast()는 한 번 나빠진 상태가 뒤 코드에 의해 되돌아가지 않도록 보장합니다. status()는 무조건 덮어쓰고 atLeast()는 나빠질 때만 올린다 — 이 구분이 이후 모든 검사 코드의 문법이 됩니다.

① SPF — 문법이 맞아도 동작하지 않는 레코드

문법 오류는 눈으로도 잡히지만, 실무에서 훨씬 흔한 실패는 10-lookup 한도 초과입니다. RFC 7208은 SPF 평가 중 발생하는 DNS 조회 횟수를 10회로 제한합니다. include는 대상 도메인의 SPF를 다시 평가하므로 재귀적으로 늘어납니다. 

example.com:  v=spf1 include:_spf.google.com include:sendgrid.net -all
                     └─ 1회                   └─ 1회                        = 2

_spf.google.com: v=spf1 include:_netblocks... include:_netblocks2... ~all   = +4

sendgrid.net: v=spf1 include:sendgrid.net a mx ...                          = +3
                                                                    ────────────
                                                                        합계 9  (아슬아슬)

한도를 넘으면 수신 서버는 permerror를 내고 SPF 전체를 무효 처리합니다. 레코드는 멀쩡해 보이는데 인증이 통째로 안 되는, 눈으로 찾기 가장 어려운 고장입니다. void lookup 제한(2회)도 있어서, 없어진 서비스의 include를 방치하면 여기 걸립니다. 

public static final int MAX_LOOKUPS = 10;
public static final int MAX_VOID_LOOKUPS = 2;

순환 참조(a→b→a)도 visited 집합으로 잡습니다.

① DKIM — 두 겹의 검사

서명 검증 DKIM-Signature 헤더를 읽고 d=/s=로 공개키를 조회해 서명을 실제로 검증 → “이 메일이 서명 이후 변조되지 않았나”
키 레코드 린트 검증이 통과해도 키 자체에 문제가 있을 수 있음
· RSA 1024 미만 → FAIL (위조 가능)
· RSA 2048 미만 → WARN
· p= 빈 값 → FAIL (폐기된 키)
· t=y → WARN (테스트 모드)

p= 빈 값이 재미있는 케이스입니다. RFC 6376 §3.6.1에서 빈 p=는 “이 키는 폐기됨(revoked)”을 뜻합니다. 폐기된 키로 계속 서명하고 있으면 겉으로는 정상인데 수신 서버는 그 서명을 무효로 봅니다.

그리고 셀렉터 문제가 여기서 풀립니다. 4장에서 “DNS로 셀렉터를 열거할 수 없다”고 했었죠. 메일이 있으면 DKIM-Signature 헤더에 s=selector1이 적혀 있습니다.

③ 헤더 품질 — 무엇을 검사하지 않을 것인가

기준선은 “정상 설정된 서버라면 자동으로 붙는가”입니다.

  • Message-ID, Date — 제대로 된 submission 경로를 지나면 MTA가 붙여줍니다. 없다는 것은 서버 설정 문제의 신호 → FAIL
